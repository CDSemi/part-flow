WorkOrderDemand never owns Movement) — which validates the canonical PN, the starting Area (active **and non-terminal** — a terminal Area is where finished quantity ends, never where production enters, so the rule lives in the Application layer and not only in the release dialog's Area list), the Operation, an active RouteTemplate when `PLANNED`, and a positive quantity within the demand's remaining quantity; requires the explicit confirmation flag when the PN already has active quantity (showing the existing distribution — never auto-creating or auto-merging); snapshots an independent AssignedRoute for a `PLANNED` release only (a `FLOATING` release has none; later template edits never alter a snapshot); creates the QuantityFlow with its route mode and `current_area_id` set by the INSERT itself; appends the immutable `RECEIVED` Movement; and commits all of it atomically. `device_event_id` idempotency stores a deterministic request fingerprint in the Movement metadata: the same id with the same fingerprint replays the original committed result, a mismatched reuse is an explicit idempotency conflict, and both create nothing; the current-position projection remains rebuildable from Movement history alone (replay verified by tests). Released state is server-derived from the immutable `RECEIVED` metadata context, with no stored counter and no migration: demand lines carry `has_released_quantity` plus their `released_quantity` and `remaining_quantity`, and a Work Order derives `RELEASED` only when every current line is fully released — a partly released line keeps it `OPEN`, and the stored status column remains `OPEN` throughout. A demand may therefore be released in **several parts** (20 of 50, then 12, then 18): each part is its own separate QuantityFlow behind the active-quantity confirmation, the remaining quantity is the hard server-side cap (a release beyond it is refused and creates nothing), and a fully released line stops offering the action. A line with any released quantity keeps only the **restricted edit** of PROJECT_PROFILE §13, enforced in the backend and not merely in the UI: `requested_quantity` (never below `max(released, allocated)` — raising it restores remaining quantity and the Work Order's derived `OPEN`), `due_date` and `job_numbers` save with their normal `UPDATED` audit row, while `request_type`, `requester`, `reason` and `notes` are refused with a 409 that writes nothing at all — not even the valid fields travelling with them — and removal stays refused; the audited Work Order header/number edit stays available (a header-only save takes no demand lock at all). The edit path locks each edited line `FOR UPDATE` and recomputes its released quantity under that lock, so a demand edit and a release of the same line serialize in either arrival order and `released_quantity > requested_quantity` is unreachable. The Add Part PN lookup is bounded server-side (at most 50 masters per listing, unchanged canonical order); the exact `number=` resolution is never bounded away, so a short but valid canonical PN still resolves exactly. Frontend: Management → Work Orders is a REAL view on the live `/api` surface (GUI_DESIGN §11 — list/search, New Work Order resolving an entered existing number instead of duplicating, Work Order Details with diff-only Save demand and draft isolation for server actions — the unsaved-changes state is the real draft-versus-saved difference, saved-line removal waits for it to be settled, and Release opens the shared `Unsaved changes` Save/Discard/Cancel decision instead of being blocked, always running on the committed demand — the §11.4 release dialog with retry-safe `device_event_id` reuse and the active-quantity confirmation flow, released lines restricted from load — Qty (flagged red at entry time when it falls below the committed quantity), due date and Job Numbers editable on an Open and on a Released Work Order alike, PN and Request Type read-only, removal blocked — while their remaining quantity stays releasable, a changed release intent taking a fresh `device_event_id`, the audited external-number edit on internal Work Orders, and the printable derived `PF:PN:` Code128 label from intake, opened from the demand-line PN itself through the ONE shared `Part Number barcode label` dialog — a provisional entry point that retargets to `Edit Part Number` in Phase 13), while the Completed Work Orders page stays an honest production placeholder (completion is derived from allocation — Phase 10) with its approved presentation behind the development-only build boundary. Phase 4 hardening (post-implementation, after the independent audits): the "one canonical PN at most once per Work Order" rule is serialized where it is written — a save that adds demand lines takes the parent Work Order row lock and re-reads that Work Order's canonical PN set under it, so two concurrent saves adding the same PN can never both create a line (lock order stays demand ascending → Work Order, matching demand removal); the active Work Order list is bounded server-side at 100 rows with `search` evaluated in the database, because nothing leaves the active list before allocation-derived completion (Phase 10) while the exact `number=` resolution stays unbounded so a duplicate number can never hide behind the bound; and the migration `0005_phase4_release_index` adds one partial expression index over `part_movements` matching the released-quantity derivation exactly (`(metadata['context'] ->> 'work_order_demand_id')::int WHERE movement_type = 'RECEIVED'`), which keeps the Phase 4 hot read path off a full scan of the append-only Movement history without adding a column, a foreign key, or a stored counter. Still deliberately absent (per this phase's scope): no Scan Station transfer and no Phase 5+ movement type (the movement-type check still admits `RECEIVED` only), no Machine assignment, no SPLIT/MERGED, no Undo/corrections, no Stockroom/allocation/completed history, no file-based import, and no real Planned Routes or full Part Numbers management (Phase 13).

## Implementation Principles

- Build in vertical slices; complete one workflow end to end before expanding.
- Never transfer quantity before the system has a real quantity-introduction workflow: Work Order Intake and production release precede all real transfer workflows.
- Preserve Presentation → Application → Domain → Infrastructure.
- Use mock data only until the relevant backend slice exists; mock behavior never leaks into production.
- Ambiguity always requires explicit confirmation before any write; unknown or invalid input is rejected with no write.
- Production writes are blocked while disconnected; offline scan synchronization is deferred and unapproved.
- Do not implement ERP integration during MVP.
