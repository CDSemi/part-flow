the current-position projection remains rebuildable from Movement history alone (replay verified by tests). Released state is server-derived from the immutable `RECEIVED` metadata context, with no stored counter and no migration: demand lines carry `has_released_quantity` plus their `released_quantity` and `remaining_quantity`, and a Work Order derives `RELEASED` only when every current line is fully released — a partly released line keeps it `OPEN`, and the stored status column remains `OPEN` throughout. A demand may therefore be released in **several parts** (20 of 50, then 12, then 18): each part is its own separate QuantityFlow behind the active-quantity confirmation, the remaining quantity is the hard server-side cap (a release beyond it is refused and creates nothing), and a fully released line stops offering the action. A line with any released quantity keeps only the **restricted edit** of PROJECT_PROFILE §13, enforced in the backend and not merely in the UI: `requested_quantity` (never below `max(released, allocated)` — raising it restores remaining quantity and the Work Order's derived `OPEN`), `due_date` and `job_numbers` save with their normal `UPDATED` audit row, while `request_type`, `requester`, `reason` and `notes` are refused with a 409 that writes nothing at all — not even the valid fields travelling with them — and removal stays refused; the audited Work Order header/number edit stays available (a header-only save takes no demand lock at all). The edit path locks each edited line `FOR UPDATE` and recomputes its released quantity under that lock, so a demand edit and a release of the same line serialize in either arrival order and `released_quantity > requested_quantity` is unreachable. The Add Part PN lookup is bounded server-side (at most 50 masters per listing, unchanged canonical order); the exact `number=` resolution is never bounded away, so a short but valid canonical PN still resolves exactly. ## Implementation Principles

- Build in vertical slices; complete one workflow end to end before expanding.
- Never transfer quantity before the system has a real quantity-introduction workflow: Work Order Intake and production release precede all real transfer workflows.
- Preserve Presentation → Application → Domain → Infrastructure.
- Use mock data only until the relevant backend slice exists; mock behavior never leaks into production.
- Ambiguity always requires explicit confirmation before any write; unknown or invalid input is rejected with no write.
- Production writes are blocked while disconnected; offline scan synchronization is deferred and unapproved.
- Do not implement ERP integration during MVP.
- Every behavior described as `deliberately absent`, `temporary`, `placeholder`, `later`, or otherwise deferred must name exactly one owning later phase, or be listed explicitly under `Deferred` / a canonical open decision. A phase must never close with an unowned target behavior.
- Before closing any phase, audit `PROJECT_PROFILE.md` + `GUI_DESIGN.md` + the current production code against this roadmap. Close the phase only when every in-scope target behavior is implemented and every intentional omission has an explicit later owner.
