# 1. Scope

Covers the application-view content of PROJECT_PROFILE §21 in **nine GUI views**:

1. Scan Station (production)
2. Production Board (monitoring, large display)
3. Area Board (monitoring — **All Areas** overview + per-Area detail; the overview carries the §21 *Manager Summary* content)
4. Machines (management, Machine lifecycle and maintenance)
5. Tracking (management, PN-centric; operator-facing label **PN Tracking**)
6. Work Orders (management, manual Work Order entry and production release — §21 *Work Orders*)
7. Planned Routes (management, reusable route definitions)
8. Priority Management (Hot Work Order Demand ranking)
9. Administration (configuration)

> **Pending PROJECT_PROFILE alignment (v4).** PROJECT_PROFILE (v8 through v13) still lists Area Board and Manager Summary as separate views in §21. GUI v4 merges Manager Summary into Area Board as its All Areas overview (no content dropped). (Two earlier deviations are now resolved: PROJECT_PROFILE v8 §8.2 defines the nullable Work-Order-level `due_date` used as the entry default for demand-line due dates, and the former "PO Intake" view name was resolved by the v7 vocabulary migration — PROJECT_PROFILE §21 names the view **Work Orders**.) PROJECT_PROFILE §21 still needs the view-merge update; until then this document notes the deviation where it occurs.

Top-level navigation exposes four entries; the management views are grouped as **sub views of one Management view**:

| Top level        | Contains                                                            |

| Scan Station     | — (single view)                                                     |
| Production Board | — (single view)                                                     |

# 2. Design System

## 2.1 One token set, two switchable themes

The application has a single global **theme mode — Dark or Light — switchable by the user**; **every view follows the selected mode** (v5; supersedes the fixed per-view themes of v2–v4).

- The toggle lives in the top navigation bar and applies to the whole application instantly, including navigation chrome, dialogs and toasts. No view has a fixed theme anymore. In Scan Station **production mode** — where the top navigation is hidden — a compact **borderless** variant of the same shared control renders in the station header's actions group **directly below the connectivity chip** in a compact vertical, right-aligned stack (§4.1), using the same global theme state (`aria-pressed`, visible focus state); the selected theme is preserved when switching between standard and production routes. The Production Board **Kiosk mode** header (§5.1) reuses the same compact borderless control.
- **Dark is the default**: PartFlow is shop-floor first — dark reduces glare in the shop, is readable from distance, and is tolerant of low-quality displays. Desk users who prefer light for dense data work switch once.
- All component styling uses **semantic tokens only** (background, panel, border, text, muted, status-text, …); the two theme definitions supply the values. Adding or restyling a component never hard-codes a theme-specific color.
- Status colors (§2.2) keep per-theme *text* variants so contrast holds in both modes (e.g. success text is bright on dark, deepened on light); status backgrounds/tints are shared. Area identity colors are identical in both themes.
- In the mockup the choice is session-only; how the real application persists it (per user, per station, or both) is an open decision (§16).

Both themes share the same color tokens, spacing scale, and typography so the product feels like one system in either mode.

## 2.2 Color tokens

Status colors (semantic, never decorative):

- **Success** `#31d287` — recorded Movement, confirmed action
- **Warning** `#ffb224` — needs attention, pending context, route deviation, due soon
- **Error** `#ff6166` — rejected scan, integrity violation, overdue
- **Info / accent** `#4f8cff` — selection, focus, primary action

Area colors: every Area has a stable identity color used consistently in **all** views (chips, dots, distribution bars, column headers). Colors are Area display properties and editable in Administration without affecting history (PROJECT_PROFILE §7 Area).

Initial palette: Material `#8b93a8`, Cut `#f5b83d`, Lathe `#3da5ff`, Mill `#9b6ef3`, Manual `#e06fae`, Deburr `#2fbf9b`, External `#ff8a4c`, Stockroom `#2fca7c`.

## 2.3 Typography

- UI text: system font stack (`system-ui, Segoe UI, Roboto…`) — no webfont dependency, works offline.
- Identifiers (PN, Work Order Number, temporary Work Order, external Job Number, Quantity Flow id, barcode values, quantities, timestamps): monospace. Identifiers must be visually distinct from prose because operators read them against paper travelers and folder labels.
- Shop-floor minimum sizes: body 16 px, PN ≥ 19 px, quantities ≥ 18 px bold. Production Board is sized for reading at 3–5 m (PN 22 px+, key figures 18 px+).
- The PN is always rendered on a single line and never wraps. Where the container cannot grow with the identifier (Area Board cards and overview lists), an over-long PN is **truncated with an ellipsis** and the full PN is shown in a tooltip on hover; layout-critical figures (quantities) must never move because of PN length. Views sized around the PN (Production Board, Tracking) keep sizing the column to fit it.
- **Realistic identifier and description shapes** (v6; PROJECT_PROFILE §8.1). PNs are opaque, commonly multi-segment hyphenated numeric strings of varying length (short `214-406` through long `0455-20-0118-03` and longer); the UI preserves the exact string, never derives meaning from segments, and search/filtering matches the hyphenated value and its punctuation literally. Work Order Numbers and external Job Numbers are likewise opaque strings — commonly numeric-looking (Work Order Number `007482`, Job Number `18427`) and never parsed, padded, or reformatted; the two are separate identifiers and are never combined. Revision is a separate optional informational field (`A`, `B`, `E`, or blank): it is never appended to the PN, and a blank Revision renders cleanly without placeholder noise. Part names/descriptions are free text — often uppercase with commas, slashes, fractions, dimensions and manufacturing abbreviations — and **may wrap naturally to two or three lines**; description wrapping must never shift quantity, status, date, or action columns (cap the description's width instead of widening the identifier column).

## 2.4 Touch and scanner ergonomics

- Minimum touch target 48×48 px; primary Scan Station actions ≥ 56 px tall.
- All production actions reachable by scan or single tap. Mouse never required on shop-floor views.
- Keyboard wedge support: the scan input is a plain text input terminated by Enter — no custom driver, no scan-mode selection (PROJECT_PROFILE §10 Barcode Model).

# 3. Global Interaction Rules

These apply to every view; they implement the profile's core principles in UI terms.

1. **Focus discipline.** On the Scan Station, the barcode input regains focus automatically after every completed operation, dialog close, session change, and view activation. Nothing may steal focus permanently. **When a scan opens a dialog, focus moves into the dialog and stays there (v16):** Enter, Escape and Tab belong to the dialog while it is open, and no pending delayed refocus may ever pull focus back out of an open modal dialog. Focus returns to the main barcode input only after the dialog closes or the workflow completes. Keyboard-wedge capture is unchanged: with no dialog open, a scan is captured completely even when the main input is unfocused (§4.4).
2. **Ambiguity requires confirmation.** Whenever a scan resolves to more than one valid production context, the UI presents an explicit choice list (§4.6). The UI never guesses and never defaults silently; nothing is recorded until the choice is made (PROJECT_PROFILE §10 Barcode Model).
3. **Feedback is tri-state and instant.** Every scan produces exactly one of: Success (green), Warning (amber — recorded but needs awareness, or an action is pending), Error (red — nothing recorded). Feedback shows *what happened* and *why* in one line each. On the Scan Station this feedback renders as a **floating notification** (§4.4) that reserves no layout space: only the most recent notice shows, it carries an explicit close button, success/neutral notices auto-dismiss after ~4 s and warnings/errors after ~8 s (a replacing notice restarts the timer). The persistent OFFLINE / DISCONNECTED banner (rule 6) is **not** a notification — it stays until connectivity is restored.
4. **Quantity integrity is visible.** Quantity entry displays the available source quantity. Attempts to move more than available are rejected with an explicit error — the UI explains the limit rather than clamping silently (PROJECT_PROFILE §11 Quantity Model).
5. **History is append-only in the UI too.** Undo appears as a new `REVERSED` entry in the scan list; the original entry stays visible. Tracking's Movement history has no edit/delete affordances (PROJECT_PROFILE §16).
6. **Connectivity loss is an explicit write-blocked state, detected fast.** Detection combines browser `online`/`offline` events with polling (no WebSocket/SSE in Phase 2): `offline` marks the application unavailable immediately; `online` triggers an immediate health check; `GET /api/health` is polled about every second with a request timeout below the probe interval and no overlapping probes; connectivity is rechecked on tab focus/visibility change. Passive probes never flip the UI to a "connecting" state — no flicker. Losing the connection shows the persistent application OFFLINE banner; production write submission is disabled while disconnected. **The banner copy is exactly `⚠ OFFLINE — Connection to the PartFlow server has been lost. Production actions are disabled` — one compact statement with no additional explanatory sentences** (no scan-queue, read-only-data or recovery explanations; the write-blocked behavior itself is the explanation on every surface). The banner renders as **two explicit regions** — the same division as the Scan Station Undo block (§4.5): the message region fills the remaining space on the left (its text wraps naturally on narrow screens — no horizontal overflow); **`Retry connection` is an independent action rail at the banner's complete right edge** — the whole region is the button element itself (never a small text button after the message), full banner height with no gap or leftover background beside it, its text centered vertically. There is **no separator element and no `|`**: a **stronger `border-left` on the rail itself** divides the regions — the station-card divider pattern. The rail carries the shared `.zone-action` presentation (always-visible light error surface; hover, focus-visible and active applied to the whole region). Already loaded read-only information stays visible where practical. No production write is queued locally, no pending Movement indicator is shown, and the UI never claims that scans will synchronize later. On reconnection, input readiness and focus are restored — the Scan Station input is re-enabled and refocused. **A scan is successful only after the server confirms the write:** connectivity status is an early warning, never permission to record a Movement optimistically. If connectivity disappears between the last heartbeat and a write request, the request fails as "nothing recorded"; the UI must never display a false recorded result (PROJECT_PROFILE §15). This rule must be preserved unchanged in the production phases. (Offline scan synchronization remains deferred and unapproved — PROJECT_PROFILE §30, §32.4.)
7. **PartFlow vocabulary everywhere.** UI labels use the canonical names: PN, WO / Work Order, Work Order Demand, Request Type (`NEW` / `MODIFY`), Route Mode (`FLOATING` / `PLANNED`), Quantity Flow, Route, Movement types (`RECEIVED`, `TRANSFERRED`, `ASSIGNED_TO_MACHINE`, `RELEASED_FROM_MACHINE`, `AREA_COMPLETED`, `SPLIT`, `MERGED`, `STOCKED`, `QUANTITY_ADJUSTED`, `SCRAPPED`, `REVERSED`, …), the user-facing DONE status with its derived `READY_TO_TRANSFER` holding state (PROJECT_PROFILE §7 Area Completion), the Repair movement intent (`movement_reason = REPAIR` — never a Request Type), Work Order Allocation, Hot (PROJECT_PROFILE §7, §8.11). A blank external Work Order Number renders as `—` everywhere (display-only — never persisted).
8. **One-shot actions, no armed state.** There is no persistent Machine Session, no armed Action barcode, and no pending PN intent that survives a dialog: every Scan Station production action is one dialog — open, complete or cancel, context cleared, input refocused. Cancel always means no write.
9. **Missing due dates are valid data.** Work Order and demand-line due dates may be absent (PROJECT_PROFILE §8.2, §8.3). A missing due date renders as `No due date` where a note line exists and as `—` as the compact/table date value — consistently, and never as an error or warning state. Wherever demand is due-date ordered, the canonical demand ordering applies (PROJECT_PROFILE §18): dated demand first, earliest first; undated demand after all dated demand, ordered by the parent Work Order's received date, with a stable deterministic tie-breaker.

10. **Professional operator copy — exhaustive.** Every rendered string is classified as exactly one of: **operator/user-facing** (explains what to do, what is required, what happens after confirmation, why an action is unavailable or rejected, and how to recover — never implementation detail), **audit/history-facing** (canonical recorded data: Movement types, workers, timestamps, Areas, Machines, quantities, reversal relationships — raw enum names are acceptable only here, i.e. the Movement history, type badges, the confirmation summary's `Recorded event(s)` row, and the Machines lifecycle audit list — `RETIRED` / `REACTIVATED` are audit data, §12.3), or **development-only** (demo barcodes, sample-data boundaries — concise, clearly isolated behind the shared `DevNotice`/dev-marked presentation, excluded from production builds, never dominating normal workflows, and never repeated per toast/dialog/footer: at most one concise development notice per view). The shared `DevNotice` is a fixed two-part structure: the compact `.dev-notice-tag` plus **one** `.dev-notice-content` element wrapping all children as a single inline text flow — long copy wraps only at natural word boundaries, never distributed across separate flex items; the notice fills its parent block's available width (`width: 100%`, `box-sizing: border-box`, `min-width: 0` — no `max-width` cap), and each `<code>` barcode value inside it is unbreakable (`white-space: nowrap`) while the sentence still wraps between values. Normal copy never exposes wording such as `(mock)`, `nothing persisted`, `local mock data`, `priority_rank`, `movement_reason`, `derived from Movement history`, or architecture explanations; legitimate operational distinctions are expressed in user language instead (e.g. `Requested quantity`, `Current recorded location`, `Complete activity history`). Cancel buttons throughout the workflows are exactly `Cancel (Esc)`. An automated rendered-copy guard (`src/rendered-copy.test.ts`) scans the renderable frontend sources (comments stripped) and the current mockup for banned developer-facing phrases, with an explicit allowlist mechanism for approved audit surfaces — canonical Movement names themselves are never banned.

11. **No false scrollbars.** The application shell derives the available content area from normal flex layout: the root is sized to the dynamic viewport (`100dvh`, with a `100vh` fallback), navigation rows keep their natural height, and the content area scrolls internally only when a view genuinely exceeds it. A view whose content fits shows **no** vertical scrollbar; content that genuinely exceeds the viewport (including the development `?state=long` previews) scrolls normally — real overflow is never hidden and dialogs, long tables and validation content are never clipped. No view duplicates a fixed navigation-height calculation (`100vh − nav`), and the navigation stays visible while content scrolls.

12. **Derived time values share one UI clock (v16).** Original timestamps (Movement times, state changes, due dates, Area-entry times) are fixed data; only the **derived** presentation values (elapsed durations, due countdowns, days in production, live clocks) change with wall-clock time. Every view derives those values at render from the fixed source timestamp plus the one shared clock (`src/components/ui-clock.ts`, `useUiClock('minute' | 'second')` — one shared subscription store per precision, never per-component timers that drift apart). Minute-precision values re-render once per minute, the live clock once per second — never faster than their precision needs. After a movement or state change the affected component re-renders immediately and re-derives from the current tick; the formatters clamp a timestamp newer than the tick to `<1m` instead of going negative. The same timestamp therefore yields the same displayed value in every view at the same moment — Scan Station, Area Board, Production Board, Tracking and Machines can never disagree. The shared derivation helpers live in `src/views/dates.ts`: `formatDuration` / `formatElapsedSince` / `elapsedMinutesSince` (one compact duration language: `<1m`, `18m`, `1h 24m`, `2d 03h`), `daysBetweenIso`, `dueCountdown` (one countdown language everywhere: `N days left`, `due today`, `overdue N days`, `No due date`; `soon` within a **lead-time-proportional Due Soon window** — `ratio` of the received → due lead time, clamped into [`minDays`, `maxDays`], derived by `dueSoonWindowDays` from the caller-supplied `DueSoonPolicy`; `DEFAULT_DUE_SOON_POLICY` carries the initial defaults — Minimum 2 days, 15%, Maximum 7 days — as the single source of truth until Administration owns the values (§9), business logic never hard-codes the numbers, and an unknown or invalid lead time falls back to the policy minimum window), and `daysInProductionNote` (`N d`). A formatted duration or countdown is never stored, and the development mocks author **relative** offsets resolved once at module load (`src/mocks/mock-time.ts`: `minutesAgoIso`, `isoDateIn`) so the sample data always shows the intended mix of states regardless of when the dev build opens — from then on the values are fixed data like real backend timestamps.

# 4. Scan Station

One screen per station, no navigation during normal production. PN-centric, one-shot actions only.

## 4.1 Station routing and selection

Three routes:

- `/scan-station` — the **Station Selector**. It never auto-redirects to a station. Each active Scan Station renders as one card with enough information to distinguish it: Station ID, Department, Area (with color), the supported Operations as **individual light informational chips** (the same shared chip presentation as the station header — never comma-joined text), and whether the Area has Machines. The card's **main selection surface is one full-card button** that opens the station in **standard mode** (→ `/scan-station/:stationId`); a separate sibling button labeled exactly **`Production mode`** opens `/scan-station/:stationId/production`. There is no standalone `Open` button and **no nested interactive controls** — the full-card button contains only presentation content, and both actions carry accessible names with the Station ID (`Open LATHE-ST-01`, `Open LATHE-ST-01 in production mode`).
- `/scan-station/:stationId` — one station in **standard mode** (e.g. `/scan-station/LATHE-ST-01`), keeping the normal top application navigation (Manager/Admin use). An unknown or inactive Station ID shows a clear error and never silently falls back to another station.
- `/scan-station/:stationId/production` — the same station in **production mode**: the top application navigation (and with it the Production Board / Management / Administration links) is hidden so operators cannot casually leave the configured station. The mode is explicit in the router model (`mode: 'standard' | 'production'`) and in the pathname — never a query parameter, hidden click, or secret gesture. It is a presentation choice only, **never an authorization or security boundary** (the browser itself stays outside PartFlow's control). Everything else is preserved: the persistent OFFLINE banner, the Worker Session, all scan/DONE/QUEUE/Undo/dialog/notification behavior, and full-viewport height with no leftover top-nav offset. Connectivity status stays visible through the connectivity chip inside the station header, with the **compact borderless Dark/Light mode control** (the same shared theme component and global state as the top-navigation toggle, §2.1) **directly below it** in one compact vertical, right-aligned header-actions stack — the narrow stack never crowds the Worker Session and never forces the Area statistics to wrap poorly at intermediate widths. **Head group height contract (v16 — refines the v15 shared-height group):** the Worker Session pill keeps its **natural height in both modes** — it is never stretched. `.ss-headgroup` uses `align-items: flex-start`; the **frameless** actions column (`.ss-headactions`) gets `align-self: stretch` with `justify-content: space-between`, and compact ONLINE-chip and theme-toggle padding keeps the actions' combined natural height below the pill's, so the pill is always the height driver — the `ONLINE` chip (which keeps its own chip frame; there is no group card and no separator) aligns its top edge with the pill's top border, the theme control its bottom with the pill's bottom border, and the header action group can never determine the Worker Session height.

Both modes share **one coherent non-interactive footer**: the faint Station ID, a subtle non-interactive mode label (**`Standard mode`** or **`Production mode`**), and the concise shortcut hint **`Ctrl+Shift+K: switch mode`**. The Station ID is never a button in either mode — the top navigation's **Scan Station** entry already returns to the Station Selector, and the footer never duplicates that behavior. The **Ctrl+Shift+K** shortcut toggles between the same station's standard and production routes (usable from the main barcode input — a scanner target the wedge capture leaves alone under modifier chords — but inert in every other text field, select, or active dialog; the dedicated route and the explicit selector actions stay the primary entry).

## 4.3 Header

The header is an explicit grid — no spacer-based wrapping. The left identity group (Department, Area name with Area color, supported Operations) and the **Worker session** pill always share the main row; the **Area statistics** sit between them while horizontal space allows and drop to a full-width second row whose cells divide the width evenly only when the single-row layout genuinely cannot fit (a real fit measurement of the three header cells' full natural widths — the identity group keeps the Department, Area name, and Operations chips each on one line, so the chips never wrap before the statistics drop — never a hard-coded breakpoint). The Worker session never wraps onto a row of its own, and the pill is **content-sized** — no fixed or minimum width; its label, Worker name, and session-window lines never wrap. There is **no Machine session pill, no Machine status strip, and no persistent active-Machine state**. The pill's sub line is the **session window**: `from <badge-scan time> to <shift end>` — the from-time is the fixed wall-clock time (`HH:MM`) of the Worker's badge scan (a new badge scan opens a new window), the to-time the shift end.

**Operations chips.** Each supported Operation renders as an individual light informational chip (subtle panel background, subtle border, rounded corners, readable in both themes, no action color, no button-like hover). Chips wrap cleanly for multi-Operation Areas; the Area name stays visually more prominent; Operation names are never parsed or modified. The chips are labels, not controls.

**Area totals with semantic tones.** The header is the **single summary surface** for Area totals (the `In this Area now` card carries no statistics block, §4.10):

- Area with Machines: Total PNs · Total pcs · Queued · On machines · Done · Hot, reconciling as `Total pcs = Queued + On machines + Done`.
- Area without Machines: Total PNs · Total pcs · Processing · Done · Hot, reconciling as `Total pcs = Processing + Done`.

Number tones follow the shared statistic tone mapping used by the Area presentation: **the PN totals (Total PNs / PNs) carry the primary text neutral (main text color) on every view, while Total pcs keeps the secondary muted neutral — the same color as the Machine-card totals line text** — and the status statistics keep their semantic tones: Queued warning, On machines / Processing information, Done success, Hot error. All tones are semantic tokens, never theme-specific hardcoded colors. The reconciling quantity values always render as numbers; Hot renders `—` when zero.

## 4.4 Scan barcode card

The Scan Barcode card sits immediately under the header and spans the full available width. The main input supports **PN barcodes**, **Worker barcodes**, and **Machine barcodes only as a one-shot shortcut** (§4.6). Action barcodes do not exist; `PF:SCRAP` in the main input is rejected — it counts only inside the Scrap workflow (§4.9). Unknown barcodes and raw PN text are rejected with nothing recorded.

There is **no dedicated ENTER button**: the scanner submits with Enter, and the input's placeholder says so — `Scan Part Number, Worker, or Machine barcode · Press Enter`. The barcode input remains the primary and largest control.

**Keyboard-wedge capture — the main input never loses a scan.** When no dialog is open, a scanned barcode reaches the main input even while the input is not focused: the first scanned character is captured (never lost) and focus then follows the scan; a barcode terminated by Enter is submitted exactly once. The capture never intercepts typing when focus is inside another text input, a textarea, a select, a contenteditable element, or an active dialog workflow; it never interferes with Ctrl/Alt/Meta shortcuts, normal button activation, or accessibility navigation; and it never merely forces focus after every click. After processing, cancellation, dialog close, Worker change, reconnect, or a completed operation, focus is restored to the main barcode input as appropriate. Unknown or ambiguous input never updates tracking data.

**Touch-primary devices (v14).** On a touch-primary device the main barcode input renders `inputMode="none"` so tapping it never raises the native soft keyboard — the input is scanner/physical-keyboard driven, never an ordinary text field. Detection uses the same shared, generalized capability-detection module as the quantity input (`src/components/touch-device.ts`, renamed from the quantity-only `quantity-touch.ts` — §4.8); physical keyboards, wedge scanners, the focus behavior, and the manual-entry dialog input (a normal keyboard field) are unaffected.

Manual PN entry stays a visible secondary action (**⌨ Enter PN manually**) placed **in the scan row itself**, at the input's right edge — visibly secondary to scanning but large enough for shop-floor use. It accepts **any non-empty, whitespace-free PN value** (PROJECT_PROFILE §7/§8.1 — created on first valid use; lowercase input is accepted and canonicalized to the uppercase PN; a value containing whitespace is rejected with an inline explanation, never silently cleaned up) and resolves the canonical PN exactly like a scan. The fallback explanation remains only as a small hint line below the scan row — no separate button row.

**Fixed card content order.** The card's DOM order is the visual, keyboard and screen-reader order — never CSS-reordered: (1) the main barcode input row with **⌨ Enter PN manually**, (2) the manual-entry fallback explanation directly beneath that row, (3) the shared `DevNotice` demo barcodes, (4) the `LAST SCANNED PN` section (§4.5).

**Demo barcodes hint = shared DEV notice (v16).** The development-only "Demo barcodes (development build only) — …" content renders through the shared `DevNotice` component — the same DEV block as the Management views (§3.10) — instead of a bespoke hint block; the former `.ss-hint` styling is gone, and `.dev-notice code` styles the barcode values — each value unbreakable while the sentence wraps between them, in the notice's single full-width inline text flow (§3.10).

**Floating scan notification.** Scan feedback does not reserve layout space in the card. It renders as one floating notification near the viewport's bottom edge: only the most recent notice shows; an explicit `×` close button dismisses it; success/neutral notices auto-dismiss after ~4 s, warnings and errors after ~8 s; a replacing notice restarts the timer, and timers are cleaned up on replacement and unmount. Notices use the semantic success/warning/error styling and alert/status live-region semantics, stay inside the viewport on narrow screens, and never cover the main barcode input or dialog actions. The persistent OFFLINE / DISCONNECTED application banner is not a notification and remains until connectivity is restored. `Last scanned PN` stays fixed inside the Scan Barcode card — only the feedback surface floats.

## 4.5 Last scanned PN and Undo

The Last Scanned PN surface lives inside the Scan Barcode card, with the **Undo action anchored to its right edge**. There is no separate Undo card and **no Recent Scans list**.

**Presentation.** The compact uppercase section label sits **outside** the block — left-aligned, directly above it, never inside the bordered surface. The block itself is **two explicit regions** — the same division as a Station Selector card: the **information region** (PN, never wrapped arbitrarily, with the movement summary beside it) fills the remaining space on the left; the **`⟲ UNDO` action region** IS the block's complete right edge — the whole region is the button element itself (never a small text button inside a larger container), flush with the right edge and full block height with no gap, spacer or leftover background beside it (the block clips its children), its icon and text centered both horizontally and vertically. There is **no separator element and no `|` character**: a **stronger `border-left` on the action region itself** divides it from the information region — the same divider pattern as the edge before a station card's `Production mode` action. The region carries the shared `.zone-action` surface (always-visible light error surface) and the shared hover, focus-visible and active treatment across the whole region. When narrow, the PN keeps the first row and the summary moves to its own full-width second row inside the information region, while the action region keeps covering the full block height at the right edge — never horizontal overflow. The block carries no bottom margin: the parent card padding is the only outer spacing below it. A disabled Undo makes the whole action region non-clickable while keeping its layout, border-left and surface (no size change): icon, text and surface dim together clearly — the information region never dims.

- Worker scans never replace the Last Scanned PN; cancelled dialogs never replace it. Only completed PN-related actions become the Last Scanned PN.
- Undo targets the most recent eligible completed PN operation and always shows a summary confirmation first: PN, original action, quantity, source and destination, Machine if applicable, Worker, timestamp, and the effect of the reversal — presented with the same structured confirmation-summary layout as the production wizards (§4.6). Cancel performs no write.
- Undo creates compensating/reversal history — the original action is never deleted. After a confirmed Undo, the Last Scanned PN advances to the next eligible previous PN operation; with nothing eligible, Undo disables.
- Future production Undo operates on the complete application command (PROJECT_PROFILE §16), not on one arbitrary Movement row.

## 4.6 One-shot workflows — temporary wizards

There is no persistent Machine Session and no persistent PN intent after a dialog completes or is cancelled. Every production action is **one temporary wizard inside one dialog lifecycle**: open → select or enter information → review a dedicated confirmation view → confirm or cancel → all temporary state cleared → focus restored to the main barcode input. The steps are views rendered inside the same modal — never nested dialogs, and the overlay never closes and reopens between steps.

Wizard rules (all workflows):

- **No production action is recorded before the final confirmation step.** Selection and entry steps never write.
- The final view is a **structured confirmation summary** (a two-column term/value layout showing only the applicable fields: Action, PN, Quantity, Request Type, Route Mode, Planned Route, Work Order behavior, Source, Destination, Machine, Area/Operation, Due date, Reason/notes, Worker, Scan Station, resulting quantity state/effect) — never one long interpolated sentence and never a note inside a dashed box. The summary uses a small optional **row-emphasis mechanism** (v12): primary operational values (PN, Quantity, Action, Source, Destination, Machine, Area, Operation, Reason when operationally important) read stronger; selected entities may render as subtle non-interactive chips; secondary audit/context rows (Worker, Scan Station, recorded event names, parenthetical notes) stay present but visually quiet. **Verification layout (v14):** the summary's label column is content-sized (`fit-content(230px)`) so values sit close to their labels instead of drifting across a fixed-width gap, and entity chips inside confirmation summaries **flatten to plain verification text** inheriting the row's size and weight — a confirmation is read-and-verify, never a set of badge-like elements (the PN keeps its monospace distinction; step recaps and selection steps keep the chip look). Nothing is hidden, labels never look like buttons, contrast holds in both themes, long values wrap safely, and color is never the only distinction. **Semantic value tones (v15):** summary values may carry a controlled semantic tone — success/recorded results use the success tone, deviations the warning tone, destructive quantities the error tone — while Worker, Scan Station and timestamps stay muted; Area values (Source, Destination, Area, `Area queue`) carry their Area color dot beside the flattened plain verification text; the tones are additive, never the only distinction, and never one color per field. The same presentation applies to every confirmation dialog, including the Undo summary.
- The confirmation view has **Back**, **Cancel (Esc)** and a **final Confirm whose label names the operation** (`Confirm receipt`, `Confirm assignment`, `Confirm transfer`, `Confirm addition`, `Confirm repair`, `Confirm scrap`, `Confirm return to queue`). Enter on the confirmation view activates the final Confirm while the operation remains valid.
- **Back preserves all previously entered values** and appears only when a meaningful previous view exists — never as a second Cancel.
- **Back to the parent dialog (v20).** A meaningful previous view includes the dialog/step the current dialog was opened from within the same workflow: every dialog opened from the PN action dialog (Machine assignment, receive/transfer, source selection, DONE, add quantity, repair, scrap) offers Back to that action dialog, a transfer opened from the source selection returns to that selection with all sources intact, and a dialog resolved from manual PN entry returns to manual entry with the entered PN preserved for correction. When one dialog is reachable through several entry paths, Back returns to the exact step the user actually came from (the stored previous step of the current workflow — context such as PN, source and selections intact). Back never records or changes tracking data. Workflows entered directly from the Scan Station surface (a scan, a monitoring row action, Undo) have no previous dialog step and show **no** Back — Cancel stays the only exit there.
- **Escape always cancels the entire workflow** from any step and records nothing; cancelled workflows never update the Last Scanned PN.
- Selection views (source selection, “Select an action”) stay selection views — they are not additional confirmation steps.
- **Dialog information hierarchy (v12).** Every dialog keeps four visually distinct layers: a neutral, concise **description** (purpose and operational consequence — no walls of text), a compact secondary **step recap** of previous selections (important selected entities such as Machine, Area, Operation or source may render as subtle non-interactive chips), **guidance** directly above the related input (§4.8), and **validation** that reads stronger than any instruction, with actionable wording and entered data preserved.
- **Focus follows the steps.** The first useful control of each step receives focus (the quantity input is focused with its value selected on quantity steps; the barcode-selection input on assignment Step 1); Back restores focus to the relevant prior control; closing or completing the wizard restores focus to the main barcode input. Wizard state is local dialog state — no Context, and no hidden Machine or PN state survives the wizard.

**Machine-first.** Scanning a Machine barcode acts only as a shortcut: it opens the Machine assignment wizard — dialog title **`Assign to Machine`** (v14; formerly "One-shot Machine assignment") — three views in one modal with the Machine preselected. The one-shot behavior is explained in natural operator language ("This assignment applies once and closes after confirmation."); implementation wording such as "persistent Machine Session" or "armed" never renders. Step 1 selects the Machine and a queued PN — the Machine **always** by explicit buttons/cards (never a dropdown), the queued PN by explicit buttons/cards by default, collapsing to a compact accessible dropdown **only while the dialog's natural height with the full PN button layout cannot fit the viewport-capped dialog height** (v20 — supersedes the former 6-item count threshold: the fit is measured from an invisible probe of the full PN button layout at the cell's width, so the decision never depends on the currently applied mode; the dialog's `max-height` cap already carries the required margin to the viewport edges; the measurement re-runs on viewport resize and queued-PN changes and returns to buttons as soon as the viewport fits them again; long PNs truncate without moving the queued quantity; a light full-width hairline separator — fading toward both ends on the subtle border token — quietly divides the Machine and queued-PN selection groups inside the dialog grid), and by a dedicated barcode input (`Scan Machine or queued PN barcode… (ENTER)`) that accepts a Machine barcode of the station's Area or a queued PN barcode; every invalid scan (unknown, other-Area or inactive Machine; PN without queued quantity; Worker/scrap/unsupported barcodes) shows an inline error and changes no selection. Scanning the second value completes the pair but never advances or records automatically. **Enter semantics on the selection page (v16):** with focus in the Step-1 barcode input, one Enter has exactly one meaning — a filled input processes the barcode as a selection scan, an **empty** input advances to the quantity page when Machine **and** PN are validly selected (regardless of whether they were selected by scan, button, or dropdown) and does nothing otherwise; the event handling consumes the keypress so one Enter can never both scan and advance. **Selection errors use the shared guidance-error style (v16):** invalid-selection feedback renders as the same inline `✕` error guidance as quantity validation (§4.8) — the bespoke `.ss-scannote` style is gone, also for the Scrap dialog's rejected-barcode note (§4.9) — and the unsupported-barcode copy is operator-facing: `Scan a Machine in this Area or a Part Number currently waiting in the Area queue. Your current selections were kept.` Step 2 enters the quantity (MAX = queued quantity, the default). Step 3 is the confirmation summary (`ASSIGNED_TO_MACHINE`, PN, quantity, Area queue → Machine, remaining queued after assignment, Worker, Station) → `Confirm assignment` → context cleared. Inactive (maintenance) Machines and Machines of other Areas are rejected with nothing recorded. No Machine context stays armed after completion or cancellation.

**PN-first.** Scanning a PN opens the applicable one-shot wizard (§4.7); entering Machine assignment from the PN action dialog preselects the PN, and Step 1's Back returns to that action dialog — the same parent-dialog Back every child of the action dialog offers (v20, §4.6 wizard rules). Worker scans switch the Worker Session (visible in the header); Worker identity never determines business correctness.

**Monitoring row actions.** In an Area **with Machines** the `In this Area now` card shows **no row actions**; assignment stays available through PN scan, Machine scan and the action dialog, and Machine-card PN rows carry **two distinct actions**, compact, icon-above-label (the icon is never the only source of meaning), each with a clear accessible name, and never merged:

- `DONE` (accessible name `Complete Area processing`, success tone) — complete processing and move the quantity to the finished state: the manual DONE wizard (quantity with MAX defaulting to the quantity at the current source position → dedicated confirmation view with Action `Complete Area processing`, PN, Quantity, Area, Machine when applicable, Result `Finished — ready to move`, Worker, Scan Station and the `AREA_COMPLETED` recorded event → `Confirm completion`). On confirmation the quantity leaves the Machine card, appears under `Finished — ready to move` in the Area summary, the current Machine is cleared and the current Area stays the physical location. Other quantity of the same PN is untouched.
- `QUEUE` (accessible name `Return to Area queue`, neutral tone) — return unfinished or paused quantity to the Area queue (`RELEASED_FROM_MACHINE`, quantity MAX-defaulted, then a dedicated confirmation view). QUEUE never marks quantity DONE.

**Direct-processing exception (v17).** In an Area **without Machines** the actively processing quantity has no Machine card to act from, so exactly the `In this Area now` rows whose portion is actively processing (`In processing`, or `External processing` at an outside vendor) carry the **single `DONE` row action** — the same shared button presentation as the Machine-card `DONE` (accessible name `Complete Area processing`, success tone, icon above the `DONE` label) in the shared separated action rail (§4.10); the PN row itself never becomes clickable and the shop-floor touch target is preserved. Clicking `DONE` records nothing — it opens the **same manual DONE wizard**, which renders no Machine field: the quantity step's MAX defaults to the actively processing quantity of the selected PN portion (a smaller quantity completes only part of it), and the unchanged confirmation view (Action `Complete Area processing`, PN, Quantity, Area, Result `Finished — ready to move`, Worker, Scan Station, Recorded event `AREA_COMPLETED`, primary `Confirm completion`) stays the only write point. On confirmation exactly one immutable `AREA_COMPLETED` Movement is recorded: the selected quantity moves from `In processing` to `Finished — ready to move`, the current Area stays the physical location, no Machine is assigned or cleared, a partial DONE leaves the remainder actively processing, other QuantityFlows of the same PN are untouched, and Last Scanned PN and Undo follow the manual DONE behavior. There is **no `QUEUE`** — a direct-processing Area has no Machine queue to return quantity to. Visibility is decided by **explicit semantic data** (Machine-less non-terminal Area + actively processing portion state) — never CSS selectors or Area names: finished (`READY_TO_TRANSFER`) portions, quantity no longer in the Area, and Areas with Machines never show the row action. While the application is offline or write actions are blocked, `DONE` is disabled in place — the action rail keeps its layout and no workflow that could lead to a falsely recorded state can open. The PN action dialog's `Complete Area processing` choice (§4.7 item 3) remains the scan-driven path to the same wizard. Management → Area Board renders the same shared card **without any row actions** and remains completely read-only.

## 4.7 PN scan resolution

1. **PN has no active Work Order Demand** (including a PN seen for the first time): the **three-step Receive Quantity wizard** opens — dialog title **`Receive Quantity`** (v16; `intake` survives only as the internal workflow name in identifiers and comments, PROJECT_PROFILE §14) — equivalent to the Work Orders “Add Part” workflow — with editable defaults `Request Type = MODIFY` and `Route Mode = FLOATING`. **Step 1 — settings (copy revised v16):** PN shown prominently; the description line carries the **PN identity only** — known PN: `This Part Number has no active production demand. Review the details below before receiving quantity.`; new PN: `New Part Number. Verify it carefully; it will be registered when you confirm the receipt.`; then directly the ℹ information guidance `No changes are recorded until you review and confirm the final step.` — the header carries **no default-explanation recap sentences** (the former `MODIFY and FLOATING are selected by default…` and `The received date is recorded from this scan…` lines are gone: the defaults and dates are visible directly in the fields); then the settings fields — review/edit Request Type, Route Mode (Planned Route only when `PLANNED`), optional due date (owned by the WorkOrderDemand; its label marks `(optional)` with the shared quiet `.field-optional` element — the reusable optional-label style, never CSS pseudo-content), starting Area/Operation, reason/notes, and the internal Work Order reuse behavior; only Tracking's Details-panel flow header keeps its compact variant, §7.2 — the semantic chip colors are unchanged); line 2: the Work Order line, where the labels `WO` and `Due:` keep normal weight while the WO Number value and the date value render bold in a slightly stronger text tone (`.ss-recap .rval`) — **text emphasis only, never a badge or an action color** — with `Notes: …` when present; then the ℹ information guidance `Enter the physical quantity received. No default quantity is assumed.` directly above the input, then keypad. **Step 3 — Confirmation:** the structured summary (Action `Receive Quantity`, PN, quantity, the same Request Type and Route Mode chips — the chip carries the route name, so there is **no separate Planned Route row** — Work Order behavior, the due date formatted as `Aug 12, 2026`, starting Area/Operation, destination state, reason/notes, Worker, Scan Station) with **`Confirm receipt`** as the only write point; the recorded description reads `received into <Area>…`. The Work Order behavior names the internal blank-number MODIFY Work Order that will be created or reused (`—`; an explicit selection dialog appears when several are plausible — never a guess). **Copy is operator-facing:** the receive, unknown-PN and manual-entry wording explains what the operator must check and what confirmation does — and internal record-creation/database wording never renders (the create-on-first-use, case-insensitivity and `received_date` engineering rules stay behind the copy, not in it).
2. **PN is not currently in the Area**: the source is resolved explicitly. One valid source → quantity view (MAX = available source quantity, the default) → dedicated confirmation view → `Confirm transfer`. The quantity view's step recap shows the transfer as source → destination Area chips plus the **Work Order context line** — never the raw `workOrder` display string: `WO` stays a plain label, the WO Number value carries the shared `.rval` text emphasis (`—` emphasized for an internal blank number), the Operation renders as the shared entity chip and a `NEW`/`MODIFY` segment as the shared Request Type chip; the display string is taken apart in **one dedicated helper** (`parseWorkOrderLabel` / `WorkOrderRecapLine`), never repeated ad-hoc parsing in JSX. Multiple source Areas/QuantityFlows → an explicit source-selection dialog first; quantities from multiple sources are never combined silently. Back on the confirmation returns to the quantity view with the source selection preserved. When the transferred quantity is still actively processing at the source (`ON_MACHINE` or direct processing), the transfer implicitly completes that processing: the confirmation identifies the completion (`Source processing: … pcs will be marked complete at the source before transfer`) and its `Recorded events` row states `AREA_COMPLETED, then TRANSFERRED`; quantity already `READY_TO_TRANSFER` (or still queued) at the source transfers with `TRANSFERRED` alone and never duplicates `AREA_COMPLETED`. Undo reverses the complete command (§4.5). Partial quantity completes and transfers only the selected quantity; the remainder keeps its source state.
3. **PN already has quantity in the Area**: an action dialog shows only the currently valid choices (a selection view — not a confirmation step):

Added quantity enters the Area queue (Areas with Machines) or direct processing (Areas without Machines).

Repair is never converted into a Request Type, and never auto-selected merely because the Area appears earlier in history — a normal transfer to a previously visited Area stays possible. Partial quantity requires a QuantityFlow SPLIT.
   - **Scrap damaged quantity** (§4.9).

## 4.8 Quantity entry

Quantity entry is a wizard step with an oversized keypad **and a real focusable numeric text input**: entering the step focuses the numeric entry and selects its value, so a physical keyboard works without clicking first. `inputMode="numeric"`, no native number-spinner. Virtual keypad buttons are `type="button"` and non-focusable (`tabIndex={-1}`, focus kept on the input), so clicking one never leaves focus where Space or Enter would re-activate it.

**Touch-primary devices (v13).** On a touch-primary device the shared quantity input suppresses the native soft numeric keyboard with `inputMode="none"` (never a permanently `readOnly` field), while the custom NumPad, selection/caret behavior, physical-keyboard input, and the MAX / CLEAR / Backspace / Enter / Escape behavior all keep working. Touch-primary is detected through **browser capability signals only** — coarse pointer, no hover, real touch points — never a user-agent sniff or a screen-width guess. Because mobile browsers honor `inputMode="none"` inconsistently, a **`window.visualViewport` fallback** runs while a quantity dialog is open: a meaningful viewport-height reduction consistent with a soft keyboard collapses the dialog's on-screen NumPad and tightens the layout so the input, guidance, validation and dialog actions stay visible; the NumPad returns when the viewport does. The detection is isolated in one shared, generalized module (`src/components/touch-device.ts`, renamed from the quantity-only `quantity-touch.ts` — v14) that also serves the Scan Station's main barcode input (§4.4), and it is fully reversible — it never touches the shared cursor-aware quantity editing semantics.

Every quantity view uses one fixed visual order: **PN → selected context or instruction → guidance/validation message → quantity input → numpad → navigation buttons**. The guidance sits directly above the input as semantic text (never inside a framed or dashed summary box, never a heavy card): the **kinds are visually distinct (v12, reduced to four kinds in v15)** — the marker-less neutral kind no longer exists; instructions and information are `ℹ` info (`Enter the physical quantity received. No default quantity is assumed.`), important constraints `⚠` warning, required actions `›` action, and validation errors `✕` error. Every guidance carries a small marker plus a thin accent edge in its semantic tone, so color is never the only distinction and validation reads strongest (`Quantity cannot exceed the 6 pcs currently available at the source.`). The validation message updates next to the input, entered values are preserved, and **Next stays disabled while the quantity is invalid**.

**Cursor-aware editing (v12).** Every shared Quantity NumPad — physical keyboard and on-screen keypad alike — applies ONE shared value-editing model: a digit **replaces the selected range at its exact position** (the selected default `4` becomes `2`, never `42`), **inserts at a collapsed caret** (`23` with the caret in the middle becomes `243`, never `234`), and **appends to the end only when the input is not focused** or no usable caret exists; Backspace removes the selection or the digit before the caret (the last digit in the unfocused fallback). After an on-screen keypad edit, focus stays on (or returns to) the quantity input with the caret directly after the inserted digit or replaced range — the caret jumps to the end only in the append fallback. Digits-only sanitization, the maximum digit count, and paste/IME sanitization all still apply.

Physical keys are handled centrally:

```text
0–9       replace the selection / insert at the caret / append (unfocused fallback)
Backspace remove the selection / the digit before the caret (last digit unfocused)
Delete    clear
Enter     advance to the confirmation view (never directly to a write)
Escape    cancel the whole workflow
Space     ignored
Other     ignored
```

Enter on the quantity step always means “advance to the confirmation view” regardless of which virtual keypad button was clicked previously; Enter on the confirmation view performs the final Confirm; Escape always cancels the entire wizard. Transfer and assignment show **MAX** and default to it; a smaller valid quantity may be entered. Add More Quantity has no MAX and no default. Next is blocked for 0 and for quantities above the available source; all server-side quantity validation requirements remain (the mock validates presentation-side only).

## 4.9 Scrap workflow

Canonical term `SCRAPPED`; UI wording “Scrap damaged quantity”. **Operator-only instruction copy (v15):** the workflow instruction reads `Scan PF:SCRAP once for each damaged piece, then enter one reason for the total. Nothing is recorded until confirmation.` — the `SCRAPPED` event name never appears in instruction copy; it renders only in the confirmation summary's `Recorded event` row and on the audit/history surfaces (§3.10). One dedicated, context-sensitive barcode `PF:SCRAP`:

- accepted **only** inside the Scrap workflow — the main scan input rejects it;
- each scan increments the pending scrap counter by one; counting changes no production state;
- the pending count can be corrected (−1) or reset before confirmation;
- a common scrap reason is mandatory;
- available, pending scrap and remaining quantities stay visible while counting;
- the **dedicated confirmation view** shows PN, Area, Machine if applicable, original available quantity, scrap quantity, remaining active quantity, Worker, Station, and reason as a structured summary;
- Cancel on any step discards the pending count with no write; `Confirm scrap` on the confirmation view is the only write point and creates **one** auditable `SCRAPPED` operation for the total.

Scrapped quantity is displayed wherever the PN appears operationally (Scan Station, Production Board, Area Board, Tracking).

## 4.10 Area and Machine monitoring layout

The shared layout (also used by the Area Board detail, §6.3):

```text
[ In this Area now ] [ Machine cards grid                    ]
[ fixed left col   ] [ Machine 1 ][ Machine 2 ][ Machine 3   ]
[ grows vertically ] [ Machine 4 ][ Machine 5 ]              ]
```

- `In this Area now` is the left column; Machine cards occupy only the right-side grid, wrap to additional rows **within** that grid, and never wrap underneath the left card (`align-items: start`). The left card may grow vertically with its PN list but never grows without bounds (its column is capped), and it is wide enough to display a normal full PN such as `2027-60-8114-00` with reasonable spacing between the left PN and the right-anchored context/quantity information; extremely long PNs truncate with an ellipsis and a tooltip. The single-column fallback is **container-aware**, not one arbitrary viewport breakpoint: when the containing view can no longer fit at least one usable Machine card beside the summary, `In this Area now` fills the full row width and the Machine cards move below it at their normal width.
- Areas without Machines render only `In this Area now`, spanning the full width — no blank Machine region.
- The `In this Area now` card uses the Area color along its top edge, presents its compact Area description (e.g. `Turning cell · Lathe 1–4`) inside the card header block exactly like the Management → Area Board → All Areas column headers — never as a separate framed or strongly divided block — and carries **no statistics block** (the Scan Station header is the single totals surface, §4.3; the Area Board keeps the statistics row on its summary card through the shared component's `showStats` option). It uses the same PN presentation language as Management → Area Board → Area with the quantity groups `On Machines` and `Area queue — awaiting Machine` when the Area has Machines, a direct `In processing` group otherwise (`Stocked` for the terminal Stockroom), and a `Finished — ready to move` group for `READY_TO_TRANSFER` quantity. DONE rows use a clear success/ready status (`done` chip; status line `Finished — ready to move`, or `Finished at Lathe 3 — ready to move` when a Machine completed the work as completion context), show their quantity, never imply the quantity is still assigned to that Machine, and remain located in the current Area until transferred. After DONE is confirmed the quantity leaves the Machine card and appears in this group; Machine cards show only actively assigned quantity.
- **PN row layout.** Each PN row is an explicit grid: production information on the left, the optional action in its own separated right-side cell:

  ```text
  ┌────────────────────────────────────────────────────────────┬──────────┐
  │ Hot + PN                         Machine/Queue · quantity  │          │
  │ WO Number · Job Numbers                         days left  │  ACTION  │
  │ in-Area status                              time in Area   │          │
  │ n scrapped                                                 │          │
  └────────────────────────────────────────────────────────────┴──────────┘
  ```

  Line 1: Hot indicator and PN left; Machine/queue/done context and quantity (formatted with `pcs`) right. Line 2: Work Order Number (`—` when blank) and external Job Number left (may truncate with an ellipsis; the complete value stays available through a `title` tooltip); the derived due countdown right (§3.12 — `N days left`, `due today`, `overdue N days`, `No due date`). Line 3, when meaningful: in-Area status left (`Awaiting Machine`, `On Machine`, `In processing`, `External processing`, `Finished … — ready to move`); time in Area right. Line 4, only when scrapped quantity exists: `{n} scrapped`. Scrapped quantity appears **only** as this readable text — the compact `⊘n` indicator no longer exists and scrap is never displayed twice. Rows inside an Area summary show their Machine/queue/completion context chip; rows inside a specific Machine card pass the explicit `showContext={false}` presentation option so the Machine already identified by the card header is never repeated per row (never hidden through fragile CSS selectors).
- **Action rail.** When a row has actions, they sit in a dedicated right-side action cell — separated by spacing and a subtle vertical border, vertically centered, with a predictable minimum width — never immediately beside the PN, context or quantity. Machine-card rows stack `DONE` above `QUEUE` inside that cell (§4.6). At very narrow widths the actions may stack below the content but stay visually separated. PN rows are never clickable as a whole. Action visibility: in an Area with Machines, `In this Area now` shows no row actions and Machine-card rows show `DONE` and `QUEUE`; in a direct-processing Area (no Machines) the actively processing `In this Area now` rows show the single `DONE` (§4.6 direct-processing exception — never `QUEUE`, never on finished rows); the Area Board passes no actions at all (read-only).
- **Machine-card operational state with age (v14, ticking v16).** Every Machine monitoring card's header status pill carries the derived operational state **with the elapsed time in that state** (`running · 1h 24m`), derived at render from the Machine's shared `stateChangedAt` timestamp plus the shared minute-precision UI clock (§3.12; PROJECT_PROFILE §8.6 — `formatStateAge` delegates to the shared duration language `18m`, `1h 24m`, `2d 03h`, `<1m`; never a stored formatted duration), so every surface shows the same age and the age **keeps ticking while the view stays open** (Machines table, monitoring cards). The operational-state tones are shared by every surface — **Running success, Idle warning, Maintenance error** — always rendered beside the written state word, never color-only. A maintenance card's empty text carries the maintenance context: `Under maintenance · Unavailable for production`, followed by the note and `expected back YYYY-MM-DD` when present. The card's totals line `N pcs assigned · M PN(s)` carries two semantic value classes — `machine-total-pcs` and `machine-total-pns` — **both sharing the secondary muted neutral of the surrounding line text and the header `Total pcs` total; the PN count deliberately stays on this secondary neutral even though the header `Total PNs` statistic carries the primary text neutral** (§4.3); semantic classes, never positional `<b>`/nth-child selectors.
- **Derived Time in Area and due countdown (v16).** A row stores only fixed timestamps — the Area-entry timestamp (`enteredAreaAt`, null where elapsed time does not apply) and the due date (`due`, ISO or null); the `Time in Area` text, its sort order, and the due countdown are all derived at render from them plus the shared minute-precision UI clock (§3.12), in the one shared duration and countdown language. A card where a countdown does not apply (the Stockroom `allocated 50/50`) shows its verbatim status through the optional `dueText` instead. Stored formatted strings (`timeInArea`, `timeInAreaMinutes`, `dueDays`, `dueClass`) no longer exist in the row model.

The dialog leads with a primary summary of the item the user moved (`Move 2027-60-8114-00 · WO 007010 from #4 to #2` plus a computed secondary line such as `2 other demands will shift down.`; the implementation action name stays secondary detail only), followed by a **`Current Position` → `New Position` two-snapshot layout** restricted to exactly the affected rank range (never the full Hot list), with **one centered downward transition arrow** between the sections — visually distinct from the per-row rank arrows. Each entry line separates rank, direction, PN, and WO/Job metadata: the rank renders first; in **Current Position** a per-row **↑/↓ arrow beside the current rank** shows where the entry will move (↑ toward rank #1, ↓ away from it), with rows kept in current rank order; **New Position** shows the order after applying, without per-row arrows — instead every row displays its complete rank transition **`#<current-rank> → #<new-rank>`** (v12): the old rank and arrow render quietly, the new rank strongest, rows stay sorted by new rank, and an entry that exists on only one side spells the missing side out explicitly — `Not listed → #n` for a restored/newly listed entry, `#n → Not listed` for a removed one — never a silent omission. **The snapshot position/rank track is content-sized AND shared by both sections (v14 — supersedes the v13 reserved-width track):** one wrapper grid encloses `Current Position`, the transition arrow, and `New Position`, and the section boxes, lists, and rows all join its tracks through a subgrid chain — so the rank/transition track sizes from the widest real value of **either** side (e.g. `Not listed → #3`) and the PN column sits at the same horizontal offset in both sections: aligned across the sections, spaced by actual content, never overlapping. The former fixed-width label/rank track (the source of the large gap between the position value and the PN) is removed, and the rank, PN and WO/Job metadata never blur together. **Snapshot divider (v15):** each section carries **one vertical rule between the shared position track and the PN column** — a single row-spanning grid item attached to the shared track's edge, never per-content-row border fragments — with the rows explicitly pinned to their grid lines so auto-placement cannot dodge the divider's cells; the divider exists only in subgrid-capable environments and is hidden in the no-subgrid fallback and in the ≤ 560 px stacked layout. The narrow-screen fallback stacks rank/transition above PN + metadata identically in both sections, keeping the rank–PN–WO/Job relationship readable. Beneath the moved-PN summary, a **compact impact/action block (v13)** states the shift impact as a readable sentence (`1 other demand will shift up.`) and separates the `Action` label from its value; the action value (`Move Down`, …) is emphasized through weight and semantic text treatment only — no decorative pill, and never louder than the moved-PN summary. The **PN** uses primary text color, stronger weight, monospace and clear spacing; **Work Order and Job Number** render as one light informational chip (`WO 007001 · Job 18112` — subtle surface/border, rounded, secondary tone, no button behavior, full metadata as tooltip) built from the explicit `workOrderNumber`/`jobNumber` fields, never parsed out of a display string. The directly moved entry is highlighted, indirectly shifted entries render with less emphasis, and an entry that exists on only one side of the change (Undo/Redo restoring a removed entry or taking back an added one) shows a clear **`Not listed`** placeholder on the side where it does not exist — never a silent omission. Buttons: `Apply ranking` and `Cancel (Esc)`. Cancel leaves the list order and both Undo/Redo histories unchanged; the visible list is **never renumbered before confirmation**. Undo and Redo confirmations use the user-facing titles `Restore previous ranking` and `Reapply ranking` and present the same snapshot layout. Adding a new entry at the bottom keeps its direct behavior (no order-change confirmation).
- **Undo / Redo instead of save-or-cancel:** every confirmed change is applied, audited, and can be stepped back and forward with Undo/Redo buttons — each step is itself an order change and shows the same confirmation. The buttons disable when the corresponding history is empty.
- A footer note restates the rules in user language: Hot demand is always worked first, in rank order, and ordering follows the canonical demand ordering — ① Hot rank ② dated demand earliest-first, with undated demand after all dated demand ordered by Work Order received date (PROJECT_PROFILE §18). Implementation identifiers (`priority_rank`, tie-breakers) never render.

## 11.2 Work Order Details — modal dialog with demand lines

- Selecting a Work Order opens a modal dialog titled **`Work Order Details`** over the list, built on the shared accessible dialog primitive (`role="dialog"`, `aria-modal`, focus trap, initial focus, Escape/backdrop close requests, responsive sizing with internal scrolling). On close, focus returns to the Work Order row that opened it.
- Primary actions: **`Save demand`** and **`Cancel (Esc)`**. Closing through Cancel, Escape, the backdrop, or any other close request never silently discards edits: a dirty draft asks for explicit discard confirmation first; a clean dialog closes directly.
- Child dialogs (Add Part, removal/release confirmations) stack correctly: only the topmost active dialog handles Escape, backdrop, and focus trapping — a child's close request never closes Work Order Details.
- Dialog header: WO Number, received date, WO due date (**editable with a calendar control while the Work Order is Open**), line count, status. **Heading polish (v15, presentation only — applies to §11.2 and §11.3):** inside the dialogs the heading renders as the shared uppercase eyebrow above the strong WO identity, with the meta line beneath it separated by a hairline divider, and the card/note width caps are lifted. Every existing protection stays unchanged: native calendar date inputs, the card-style demand-line layout at narrow widths, the dirty-close discard confirmation, released-line read-only protection, focus on the first invalid control after a failed save, and correctly stacked sibling dialogs.
- **WorkOrderDemand rows:** an editable table, one row per PN demand: PN (lookup or create — any non-empty, whitespace-free PN text is accepted and created on first use, canonicalized to the uppercase PN; whitespace is rejected, never silently removed), Request Type (`NEW` default / `MODIFY`), requested quantity, due date (calendar control), priority when applicable, external Job Numbers, requester / reason / notes. Long WO line lists scroll with a sticky header and a line count.

Add Part manually opens the multi-step Add Part dialog of §11.3 (PN → quantity → due date → optional metadata). Barcode scanning remains available as a **secondary, optional method**: it accepts only valid PN barcodes and rejects unknown barcodes. A new line joins the Work Order as a visibly marked **unsaved draft** — Request Type defaults to `NEW`, the due date defaults to the WO due date when one exists. Scanning or entering a PN already on the Work Order focuses the existing line instead of adding a duplicate; a released line is announced as read-only instead.
- **Removing demand lines (v6)** follows the canonical Work Order Demand removal rule (PROJECT_PROFILE §13):
  - an unsaved draft line is removed immediately;
  - a saved line with no released production quantity is removed only after an explicit confirmation dialog;
  - once any quantity has been released to production, the line's remove action is disabled with the explanation "Cannot remove: production quantity has already been released." — later adjustments go through correction/production workflows, never deletion;

An **inactive PN** is flagged and cannot be released without reactivation.

After a failed save the first invalid control receives focus and all entered values are preserved.

## 11.3 New Work Order — manual-first modal dialog and Add Part flow

- **Presentation (v6):** New Work Order opens as a **modal dialog over the WO list**. The dialog has `role="dialog"`, `aria-modal="true"`, an accessible name from its visible heading, initial focus inside the dialog, keyboard focus trapping, Escape and backdrop-click close requests, focus restoration to the **＋ New Work Order** button on close, responsive sizing with internal scrolling for long line lists, and follows both theme modes. The URL never changes.
- **Nothing is silently discarded:** Escape, backdrop click, Cancel, or any other close request on a dialog with entered data first asks for explicit confirmation ("Discard this New Work Order?").
- **Header form (v8):** WO Number (**optional**), received date (calendar control, defaults to today, always available), and **WO due date** (calendar control, **optional**) — the default due date for demand lines when set. The dialog explains the consequences plainly: a blank WO Number saves an internal Work Order with a **null** number that displays as `—` and may receive the real external number later through an audited edit (PROJECT_PROFILE §7 — no temporary number is generated); due dates can be added later; the Work Order can be saved without a due date. Entering a WO Number that already exists opens the existing Work Order instead of duplicating it — **duplicate handling applies only when a WO Number was entered**; if lines were already entered, opening the existing Work Order is confirmed explicitly first. The uniqueness check spans the **whole history including completed Work Orders** (post-v17): entering the number of a completed Work Order announces the completion and opens its read-only details (§11.5) — a completed number is never silently reusable just because the Work Order left the active list.
- **Manual Part addition is the primary workflow (v7):** a prominent **＋ Add Part manually** action opens **one accessible multi-step dialog** (no stacked nested modals):

## 11.4 Demand save vs. production release

- **Save demand** persists the WorkOrder and WorkOrderDemand rows only. Saving never creates production quantity — the UI states this explicitly ("business demand — separate from production").
- Each saved demand row carries an explicit **Release to production…** action. Releasing opens a confirmation flow that:
  1. confirms the release quantity;
  2. confirms the Route Mode — `FLOATING` (default, no Route required) or `PLANNED` with a selected Route (snapshot noted);
  3. confirms the configured starting Area and Operation;
  4. **warns when the PN already has active quantity**, showing the existing distribution and requiring explicit confirmation of intent — never auto-creating or auto-merging quantity;
  5. shows a **release summary before commit** (PN, quantity, Route, starting Area/Operation, Work Order Demand);
  6. on Confirm, reports the result: created Quantity Flow id, assigned Route, starting Area, quantity, and the appended `RECEIVED` Movement.
- Saving demand never triggers a release automatically; release is always a separate explicit action.

## 11.5 Completed Work Orders page (post-v17)

Read-only history of every completed Work Order (completion = every Work Order Demand fully allocated, PROJECT_PROFILE §8.2). The page lives on its own route, `/management/work-orders/completed`, inside the Work Orders sub view: entry is the quiet secondary **`Completed Work Orders ›`** toolbar action on the active WO list (§11.1) plus the list PageNote's link; the page leads with a **`‹ Work Orders`** back action returning to the active list. Completed Work Orders are retained **permanently**, so the page is designed for an unbounded list from the first day: search, filtering, ordering and paging are a server-side contract over the whole history (Phase 2 simulates it against a generated mock dataset large enough to exercise paging), and the page never assumes the history fits in one response.

- **Done date is the page's central value:** the Work Order's `completed_at` (PROJECT_PROFILE v15 §8.2) — the timestamp of the allocation event that fully allocated the last open Work Order Demand. A later audited allocation correction can make the Work Order incomplete again (§8.2): it then leaves this page and reappears in the active list — nothing is ever deleted, and the allocation audit trail keeps the full story.
- **Own toolbar, independent of the active list:** a search field over **WO Number, PN and Job Number** (history lookups usually start from a PN or a Job Number, not only the WO Number), a **Done range** select with the presets `Last 30 days` / **`Last 90 days` (the default)** / `This year` / `Last year` / `All time` / `Custom…` (Custom shows two native date inputs, §11 date conventions), and a **Due outcome** select `All` / `On time` / `Late` / `No due date` for quick delivery-performance queries. The default 90-day window keeps the initial query and the visible list honest against years of history; it is presentation state only — never persisted, never silently widened. Search and filters combine (AND).
- **Result summary line** under the toolbar restates what is actually shown — count, loaded/total and the effective range (e.g. `Showing 50 of 1,248 completed Work Orders · last 90 days`) — so a bounded view is never mistaken for "everything".
- **Table** — columns **WO Number | Done | Received | Due | Demand lines**. There is no Status column (every row is Complete) and no due-date urgency ramp (§3.9 lateness never applies to completed work). The **Due** cell carries the date plus a quiet derived outcome line — `✓ On time` / `✕ N days late` (done vs due) / `—` when the Work Order had no due date — the ✓/✕ markers keep the signal non-color-only (§12.3/§12.4 idiom). Internal Work Orders render exactly as on the active list (`—` plus the internal label); demand lines keep the count + PN preview presentation.
- **Sorting:** the date and identity columns carry the shared sortable headers (§12.1 — `aria-sort` on the th, ↑/↓ arrow, faint ↕ while inactive, stable order). The initial sort is **Done descending** (most recently completed first), and the unsorted state of the cycle returns to that default — an unbounded history has no meaningful "registry order".
- **Paging:** the page loads the newest 50 matching rows; a **`Show more`** action appends the next 50 (keyset continuation on `(completed_at, id)` — never offset paging over an unbounded table). Changing search, filters or sort resets the paging; the summary line keeps the loaded/total counts visible.
- **Row activation** follows the shared whole-row pattern (§11.1 — row button `Open Work Order {no}`, Enter/Space, visible focus treatment): activating a row opens the same **Work Order Details** dialog (§11.2), read-only exactly as for every non-Open Work Order, with **`Done <date>`** added to the dialog's meta line; closing returns focus to the row and the URL never changes for the dialog.
- **Empty states distinguish "none ever" from "none in this range":** with no completed Work Orders at all, a plain empty state; with filters active, `No completed Work Orders match in this range — widen the Done range or clear filters.`; and when a **search text** finds nothing inside a bounded range, the empty state additionally offers a one-click **`Search all history`** action (clears the Done range, keeps the search) — a Work Order must never be presumed missing just because it completed outside the default window.
- The page is history only: it offers no New Work Order, no editing, no release actions, and its toolbar state is fully independent of the active list's search. Presentation (table, states, responsive behavior) matches the WO list (§11.1); in Phase 2 the page reads generated mock data and the single per-surface `DevNotice` states the sample-data boundary once.

The header carries a direction arrow (`↑`/`↓`; a faint `↕` while unsorted marks the column as sortable), and the active sort renders emphasized in the info tone (bold + info text color); the owning `th` carries `aria-sort`. Sort values: Machine = display name; State = derived state ordered Running → Idle → Maintenance; Assigned now = total assigned quantity; Asset = Asset Tag; Maintenance = override on before off. The sort is stable — equal values keep name order, then the registry order.

- **Machine** — display name with the Area beneath it (Area color dot + name).
- **State** — the derived operational state with its elapsed time (`Running · 1h 24m`): (1) an explicit **Maintenance** override wins; (2) otherwise assigned active quantity means **Running**; (3) otherwise **Idle**. Users never choose Running/Idle by hand. The age derives at render from the shared `stateChangedAt` timestamp plus the shared minute-precision UI clock (§3.12 — compact formats `18m`, `1h 24m`, `2d 03h`, `<1m`; never a stored formatted duration), so this view, the Scan Station and the Area Board always show the same age and the age keeps ticking while the view stays open (§4.10). Under maintenance a quiet secondary line shows the note and `Expected back YYYY-MM-DD` when present. The column is content-sized to its widest `<state> · <age>` line, which never wraps; the maintenance note wraps beneath it.
- **Assigned now** — the PN portions currently assigned to the Machine with their quantities (`pcs`), or `—`. The separator and the `pcs` unit stay faint; the quantity carries the information tone while the Machine is Running and the error tone while it is under Maintenance — an additive signal the State column keeps redundantly, never the only distinction.
- **Asset** — asset tag, manufacturer and model as quiet metadata. The column is content-sized: **both** the `Asset <tag>` line and the manufacturer + model line never wrap, so the widest of the two defines the column's minimum width; manufacturer and model render in two distinct neutral tones (muted vs. faint) so they read as separate values without becoming statuses.
- **Maintenance** — an **On/Off switch** per row (`role="switch"`, `aria-checked` mirroring the real maintenance state, accessible name `Maintenance — {name}`). Toggling never changes state directly — it only **opens the existing dialogs**: Off → On opens Start maintenance (§12.2), On → Off opens the Clear maintenance confirmation; the switch reflects reality only after the dialog confirms.
- **Whole-row activation (v15):** clicking anywhere on a row opens the Edit Machine dialog (§12.3); the name cell's row button (accessible name `Edit {name}`) is the keyboard/screen-reader entry with Enter/Space activation and a visible focus treatment. The Maintenance cell is the row's one interactive island — it stops propagation so operating the switch never opens the dialog.

## 12.2 Maintenance

Maintenance is an explicit override and nothing more:

- it may start while quantity remains assigned — the dialog states plainly that the assigned quantity stays exactly where it is (`… pcs stay assigned to it — nothing is moved or released by this action.`); starting maintenance never moves, releases, completes or transfers quantity and never rewrites history;
- the Start maintenance dialog collects an optional reason/note and an optional expected return date;
- while a Machine is under maintenance, the Edit Machine dialog (§12.3) carries an editable **Maintenance** section — reason/note and expected return date, prefilled and saved with the normal `Save changes` — updating the context in place without touching the maintenance start time or the state itself; the section states that Maintenance is switched off from the Machines list;
- clearing maintenance returns the Machine to **Running** when quantity is still assigned, otherwise to **Idle** — the confirmation names the resulting state.

## 12.3 New Machine / Edit Machine dialog

There is **no barcode input, no Asset Tag input, and no explanatory sentence under the values**: the Asset Tag is assigned automatically when the Machine is created — the next value in the format configured in Administration → Barcode configuration (PROJECT_PROFILE §8.6) — and the barcode derives from it (`PF:MACHINE:<asset-tag>`, §10). On an **existing** Machine the header additionally carries the **fixed Area** as a full-width row (label-row color line, Area color dot + name, and the quiet service-life explanation: the Area is set at creation and stays fixed for the whole service life; moving capacity is a replacement — retire + new record) and the **`Barcode label…`** action opening the printable label dialog (below).

Metadata is optional — production tracking never depends on it; the required **Asset Tag identifies the physical asset** even when display names are reused, and is never one of these editable fields. Every text field carries a realistic `e.g. …` example placeholder (the native date input shows the browser's own format hint instead).
- **Adding is staged (new Machine):** the form's primary action is `Continue` — it validates and leads to a **`Confirm new Machine` summary** stating that nothing has been added yet and recapping the Machine, Area, Asset Tag, barcode and whichever optional metadata was entered, with `Back` returning to the form with its input intact. Rendered barcode values (`PF:…`) share this ONE muted mono reading tone on every surface — the confirmation summaries, the identity headers (§12.3, §12.4), the retirement consequences list, and the Administration barcode-configuration preview (§9) — through one shared style; a barcode is identification data, never emphasis. The summary's `Add Machine` action asks one final explicit question (`Add this Machine?` — a Machine record cannot be deleted once added, it can only be retired later) in the **attention confirmation variant** (§12.4 Retire flow — warning tone: permanent but constructive); only its confirmation really adds the Machine.

## 12.4 Retirement, reactivation and replacement

- **Retirement is blocked while active quantity is assigned:** the Danger Zone communicates this **in place** (§12.3 — blocked message, disabled `Retire…`); the `Cannot retire Machine` dialog (`Close` as the only action) remains as the fallback for a stale view or race, and the real gate stays in the production workflow — never presentation-layer only.
- **Retire flow (v15 — from the Edit dialog's Danger Zone, §12.3; two-step confirmation and recorded edits decision v17):** starting Retire with unsaved edits first requires an explicit three-way decision through the shared `UnsavedChoiceDialog` — `Save changes` / `Discard changes` / `Cancel (Esc)` (the save choice is disabled with a stated reason while the form is invalid); edits are never saved silently. The choice is a **recorded decision, not an immediate action**: nothing is saved or discarded until the retirement completes, so cancelling any later step returns to the Edit dialog with the edits still in the form. Then the shared `TypedConfirmDialog` (`Retire Machine`) — **danger-toned across the whole dialog** (error border, faint error surface wash, error-toned eyebrow title; the `Confirm retirement` summary below shares the same treatment), so the destructive context never reads as routine, and with **initial focus on the typed-confirmation input** (the gate is the dialog's task) — requires **typing the Machine's Asset Tag** — always present, never the reusable display name — matched with trimming, case-insensitively, after an explicit consequences list: the Machine disappears from assignment choices; its barcode (`PF:MACHINE:<asset-tag>`) no longer accepts assignment scans; all history is preserved and nothing is deleted; the record moves to Retired Machines, and only the same physical machine can later be reactivated. Its confirming action is `Continue` (v17): it leads to a final **`Confirm retirement` summary** stating that nothing has changed yet and recapping the Machine (as it will be retired — with the edits when the recorded decision is Save), Area, Asset Tag, derived barcode and the recorded edits decision, with `Cancel (Esc)` / `Retire Machine`. The summary's `Retire Machine` action asks one last explicit question (`Retire this Machine?` — the retirement is recorded permanently in the Machine's lifecycle and cannot be undone; even a later return to service keeps it in the record) in the **attention confirmation variant** (centered icon badge with a tone halo, emphasized sentence-style title, tone-washed surface, and the description itself in a soft wash of the same tone — light red here, light amber for the warning finals — with the Machine name and the cannot-be-undone statement in the full text tone; the copy of every final question leads with what happens and states explicitly that the action **cannot be undone**, so the variant interrupts reflexive confirmation instead of reading as a routine notice); only its confirmation retires the Machine: it applies the recorded edits decision, appends a `RETIRED` lifecycle audit event (§12.3) and sets the retirement date; a Machine ever referenced by history is **never hard-deleted**. Operator wording is `Retired`, `Retire Machine`, `Retired on …`.
- **Retired Machines table:** columns **Machine | Retired | Asset | Notes** — name + Area, `Retired on YYYY-MM-DD`, asset metadata, notes; historical display and reporting with **no action column**. All four columns carry the same sortable headers as the active table (§12.1 — Machine = name, Retired = retirement date, Asset = Asset Tag, Notes = notes text), sorting independently of the active table's sort state. **Whole-row activation opens the read-only Retired Machine Details dialog** (same pattern as the active rows: the name-cell button — accessible name `Machine details — {name}` — is the keyboard/screen-reader entry), and the details dialog carries the only `Reactivate` entry. Retired Machines still never appear in assignment choices and accept no new scans.

The display name is editable in the dialog and **shares one form row with the Area select** (`Return Area`, active non-terminal Areas, the shared label-row color-line preview §12.3); each column carries its own feedback directly under its input. Under Display name: a name collision with an active Machine of the target Area shows the inline error `✕ “<name>” already exists in <Area>.` scoped to the name column, and renaming resolves it (display names must be unique among the **active** Machines of one Area; reuse across time stays allowed); a valid non-empty name shows the success-toned availability confirmation (`✓ “<name>” is available in <Area>.` — the ✓/✕ markers keep the signal non-color-only). # 13. Planned Routes (Management)

Management sub view on `/management/planned-routes` (follows the global theme mode, §2.1): reusable route definitions — internal domain name `RouteTemplate` (PROJECT_PROFILE §8.8) — for authorized production roles, permission-based like Machines (§12; PROJECT_PROFILE §20). The user-facing name **Planned Routes** keeps the definitions clearly apart from the **Floating actual route traces** shown in Tracking (§7.2). Planned Routes guide production; they never replace or rewrite the actual immutable Movement history.

## 13.1 Route template list

A searchable list (route name, Operation) with a **+ New Planned Route** action, **split into two tables like Machines (v15)**: an **Active** table (columns **Planned Route | Steps | Status | Used by** — no Actions column) and a separate **Archived Routes** section (columns **Planned Route | Steps | Archived | Used by | Duplicate**):

- **Planned Route** — name with the optional description beneath it.
- **Steps** — the ordered step sequence as **Area-colored chips (v15)**: each chip carries a tinted surface (`color-mix` of the Area color into the panel), an Area-colored border, the Area color dot, and the Area name in the normal text color; the arrows between chips are separate sibling elements. Without `color-mix` support the chip falls back to the neutral chip surface — the dot and border still carry the Area identity, so color-mix is never load-bearing.
- **Status** — `Active` with its updated date (active table); the archived table shows the archived date, rendered visually quiet.
- **Used by** — `N Quantity Flows…` opening the usage dialog, or `Never used`.
- **Whole-row activation (v15):** clicking anywhere on an active-table row opens the Edit dialog (§13.2); the name cell's row button (accessible name `Edit {name}`) is the keyboard/screen-reader entry, and the usage cell stops propagation so opening the usage dialog never opens the editor. `Duplicate`, `Archive…` and `Delete…` live **inside the Edit dialog** (§13.2/§13.3), not on list rows. **Archived rows are not clickable and offer only their per-row `Duplicate` button.**

The **usage dialog** lists the Quantity Flows released with the template — flow id, PN, released date — and states that each keeps its own route snapshot from release time.

## 13.2 Create / Edit dialog

- Fields: route name (required), optional description, and the **ordered steps** under a labelled column header row (Area / Operation / Est. time / Preferred Machine) — each step row presented like a Priority item: drag grip, step index, the step fields, ↑/↓/✕ controls, and a labelled Instructions line beneath.
- **Steps reorder with drag-and-drop plus explicit up/down controls (v15 — supersedes the v13 "no drag requirement"):** drag-and-drop is supported like the Priority list, with **Move Up/Move Down kept as the keyboard/touch path — reordering is never drag-only**; remove buttons stay per step, and an **+ Add step** action appends a step. At least one step is required.
- **Operation is a select scoped to the chosen Area's Operations (v15).** A stored Operation no longer offered by the Area renders as an explicit `{operation} (unavailable)` value — kept visible, **never silently cleared**.
- **Preferred Machine is a select over the chosen Area's ACTIVE Machines, referenced by stable Machine id** (matching `preferred_machine_id` — display names are reusable and cannot identify a preference), with `— no preferred Machine` as the default. A referenced Machine that is retired or missing renders as an explicit `(unavailable)` value (`{name} — retired (unavailable)` / unknown id) — kept visible, never silently cleared.
- **Changing a step's Area resets and revalidates its Operation and Preferred Machine:** the Operation is kept only when the new Area still offers it, and the Preferred Machine only when it belongs to the new Area.
- The step comboboxes size to their content (`max-content`, capped) and go full-width at the phone breakpoint; the bottom-border-only duration and instruction fields keep their labels and a visible focus state.
- Unsaved edits are visibly marked (`● Unsaved changes`), the cancel action is exactly `Cancel (Esc)`, and closing a dirty dialog asks `Discard unsaved route changes?` before discarding.
- **Editing a used template shows an explicit note:** changes apply to **future assignments only** — the Quantity Flows already released with this route keep their Assigned Route snapshots unchanged, and an in-production Assigned Route is changed separately in its own audited workflow with a reason (Tracking → `Edit assigned Route…`, §7.2 Corrections), never here.
- **In-dialog actions (v15):** `Duplicate` plus `Archive…` (ever-used) or a destructive-toned `Delete…` (never-used only) live in the dialog. Starting Duplicate with unsaved edits requires an explicit choice (`Save, then duplicate` / `Duplicate the saved route` / `Cancel (Esc)` — shared `UnsavedChoiceDialog`); `Duplicate` copies the template (including an archived one, from its table) into a new never-used active `{name} (variant)` draft and opens it for editing.

## 13.3 Archive versus delete

- **Delete exists only for never-referenced templates** — the confirmation states that the route has never been used by a released Quantity Flow, so it can be removed completely; it stays a plain destructive confirmation dialog.
- **An ever-used template archives instead**, guarded by a typed confirmation (v15): starting Archive with unsaved edits first requires an explicit `Save changes, then archive` / `Discard changes` / `Cancel (Esc)` decision (shared `UnsavedChoiceDialog`); then the shared `TypedConfirmDialog` (`Archive Planned Route`) requires **typing the exact route name** (matched with trimming, case-insensitively) after the four-part consequences warning — the route is no longer offered for future assignments; the Quantity Flows released with it keep their Assigned Route snapshots; actual Movement history is unchanged; the route stays visible for historical context.
- Archived templates are never offered for new route assignments.
- There is **no separate template-versioning system**: existing Assigned Route snapshots preserve the historical route definitions (PROJECT_PROFILE §8.8, §8.10).

## 13.4 States and Phase 2 boundary

Loading, error and empty states follow the standard view-state presentation (`No Planned Routes defined yet.` / no-match message). In Phase 2 the view edits development-only mock state (one concise `DevNotice`); the mock templates include a used active template, an archived previously used template, and a never-used draft so every action path is demonstrable.

## 14.11 Changes from GUI Design v7

All v7→v8 changes are implemented in the Phase 2 frontend against development-only mock state; the corresponding domain rules are canonical in PROJECT_PROFILE v9.

1. **PN-centric one-shot Scan Station, no Machine Session** (§4): the Machine session pill, Machine status strip, persistent active-Machine state, armed Action barcodes (`PF:ACTION:…`) and the Recent Scans list are removed. Scanning a Machine barcode is only a one-shot assignment shortcut; scanning a PN opens the applicable one-shot dialog (intake / source-explicit transfer / action dialog with only currently valid choices); completing or cancelling a dialog clears every temporary context. The header carries Area statistics instead of Machine-session state; the Scan Barcode card spans the full width directly under the header; the Last Scanned PN surface carries the Undo action at its right edge with a summary confirmation before every reversal.
2. **Scan Station routing** (§4.1): `/scan-station` becomes a Station Selector (never auto-redirecting); `/scan-station/:stationId` loads one station; unknown/inactive Station IDs show an explicit error; the faint footer Station ID was made clickable for switching (historical — the footer has been fully non-interactive since v13, §14.6 item 2).
3. **Request Types reduce to `NEW` / `MODIFY`; Repair becomes a movement intent** (PROJECT_PROFILE §7, §14): REWORK is removed everywhere; MODIFY intake creates/reuses an internal blank-number Work Order (`work_order_number = NULL`, displayed `—`); Repair is an explicit `TRANSFERRED · movement_reason REPAIR` chosen by the user (“Send quantity here for repair”), never inferred from route history and never new demand.
4. **Floating Routes by default** (PROJECT_PROFILE §7, §17): every Quantity Flow carries `route_mode` (`FLOATING` default / `PLANNED`); AssignedRoute snapshots exist only for Planned flows; Tracking shows the route-mode badge and derives Floating actual traces from Movement history with repeated Areas and explicit `⟲ REPAIR` markers (§7.2).

8. **Auditable quantity addition** (§4.7): “Add more quantity” is operator-allowed with a mandatory reason, no MAX and no default, summarized and confirmed, represented as `QUANTITY_ADJUSTED · direction INCREASE` — never an ordinary transfer, never changing requested quantity.
9. **Two Area modes only** (PROJECT_PROFILE §12): no Machines → direct Area processing (`Machine = NULL`, no queue, no placeholder cards, no zero-value statistics); one or more Machines → `QUEUE_AND_ASSIGN` with one-shot assignment (`ASSIGN` on queued rows, `QUEUE` on Machine rows); single-Machine auto-assignment is removed.

11. **Quantity keypad keyboard fix** (§4.8): a real focusable numeric input opens focused (`inputMode="numeric"`); keys are handled centrally (0–9, Backspace, Delete, Enter=Confirm, Escape=Cancel, Space ignored); keypad buttons are `type="button"`, non-focusable, and never re-activate on Space/Enter; MAX exists (and is the default) only for transfer/assignment.
12. **Administrative archival/purge specified** (§9; PROJECT_PROFILE §28): PN archive (soft-delete) with `(archived)` markers and preserved historical text; Admin-only history archival & purge maintenance with preview, reason, and audit; archive preferred over purge; retention settings in Administration. Phase 2 carries these as specification placeholders only.

## 14.12 Changes from GUI Design v6

All v6→v7 changes are implemented in the Phase 2 frontend against development-only mock state; the corresponding domain rules are canonical in PROJECT_PROFILE v8.

1. **Fast connectivity detection with a strict write-confirmation rule** (§3.6): browser `online`/`offline` events plus ~1 s polling of `GET /api/health` (request timeout below the probe interval, no overlapping probes), recheck on tab focus/visibility, no "connecting" flicker from passive probes, and Scan Station input re-enable and refocus on recovery. A scan is successful only after the server confirms the write — connectivity status is an early warning, never permission for optimistic recording; a write that cannot reach the server fails as "nothing recorded". WebSocket/SSE remain out of scope for Phase 2.
2. **Missing due dates are valid data** (§3.9, §11; PROJECT_PROFILE v8 §8.2/§8.3): WorkOrder and demand-line due dates may be absent, rendered as `No due date` / `—`; "missing due date" is removed from the validation error list; ordering everywhere follows the canonical demand ordering (PROJECT_PROFILE §18 — dated earliest-first, undated after all dated demand by Work Order received date, stable tie-breaker).
3. **Work Orders becomes manual-first with optional identifiers** (§11): WO Number and WO due date are both optional; a blank WO Number generates a temporary internal `TMP-YYYYMMDD-HHMMSS` number on confirmed save; **＋ Add Part manually** is the primary workflow through one accessible multi-step Add Part dialog (PN → quantity → due date with explicit "No due date" → optional metadata, backward navigation preserving values); barcode scanning is demoted to a secondary optional method (the Scan Station remains scanner-first); Save demand shows an omission-summary confirmation before saving. The modal-over-list architecture and URL behavior of v6 are unchanged; no new route is added.
4. **Scan Station refinements** (§4): the Station ID leaves the header and becomes a faint bottom-edge diagnostic caption ("Station LATHE-ST-01"); manual PN entry becomes a visible secondary action **⌨ Enter PN manually** with an explanatory caption; recent scans carry the Movement type as an explicit field (`movementType: MovementType` in the mock model) rendered as its own badge plus a recorded/reversed status — never embedded at the start of description strings; the quantity dialog gains full physical-keyboard support (digits, Backspace, Delete/Clear, Enter, Escape).
5. **Production Board hardening** (§5): live local date-and-time header clock (self-updating component, no static mock clock); standard Hot Part presentation `🔥#1 <PN>` via one shared component (`HotPn`, `src/components/indicators.tsx`) used on Production Board, Area Board, Tracking and Priority; only the due-date urgency text blinks (PN and date stay steady; `prefers-reduced-motion` honored; footer legend updated); stable Areas & Quantities grid with vertically aligned quantities; column order moves Job Numbers last (No. · Part Number · Areas & Quantities · Time · Due Date · Total Days · Job Numbers) with content-driven `colgroup` sizing; **dynamic pagination** measured from actual board and row heights replaces the former fixed rows-per-page assumption (12 s rotation only when more than one page exists; 10-row fallback in layout-less DOM environments).
6. **Area Board per-Area detail redesigned** (§6.3): the "one card per PN" grid is replaced by an Area summary card (name, description, Operations, stats, grouped compact PN list — Assigned to Machines / Area queue / Stocked for terminal Stockroom) followed by one monitoring card per Machine (running / idle / maintenance with distinct empty and maintenance presentations, from the `MOCK_AREA_MACHINES` mock model); Areas without Machines render only the summary card; "Sort: Time in Area" works via the sortable `timeInAreaMinutes` duration field, longest first.

## 14.13 Changes from GUI Design v5

All v5→v6 changes concern the Work Orders view (§11) and the canonical vocabulary; Phase 2 implements them against development-only local mock state.
